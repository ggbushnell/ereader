# pokered.pack format, 2026-09-12

The asset pack the reader's Pokemon companion screen draws from. Generated by
`tools/pokered_pack.py` out of a pret/pokered checkout
(`third_party/pokered`, gitignored) into
`build_pack/pokered.pack` (also gitignored). The repo ships the
generator, never the assets. The file is uploaded through the games page like a
ROM and lands at `GAMES_PACK_PATH` on the reader, where `src/pack.cpp`
reads it.

Run it with:

```
cd ereader && python3 tools/pokered_pack.py
```

Pillow is used when present, purely as a PNG decoder; a pure `zlib` reader in
the same file covers a machine without it, because every pokered PNG is a plain
non-interlaced grayscale image.

## Container

Little endian throughout.

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `EPK1` |
| 4 | 4 | section count `n` |
| 8 | 24 `n` | table of contents |
| 8 + 24n | ... | raw section bytes, in table order |

Each table entry is `char name[16]` zero padded (names are at most 15
characters), then `u32` offset from the start of the file, then `u32` length.
`src/pack.cpp` caps the count at 48. This pack uses **39 sections**, so nothing
had to be merged to stay under the cap.

## Pixel conventions

Every graphic is converted to Game Boy tiles from the source PNG, **row-major
tile order** (left to right, then top to bottom over the source image). That is
worth stating plainly for the Pokemon pics: the ROM's own decompressor writes
them column-major, but this pack does not, so the firmware blits a pic's tiles
straight across each row.

- **Shade**: 0 white, 1 light gray, 2 dark gray, 3 black. The pokered PNGs are
  2 bit grayscale with samples 255/170/85/0, so `shade = 3 - sample / 85`,
  which means lighter = lower index. Shade 0 is the sprite transparency value
  the layout doc relies on.
- **2 bpp**: 16 bytes per 8x8 tile, one row at a time, low bitplane byte then
  high bitplane byte. Pixel 0 is the leftmost and sits in bit 7. This is
  exactly what `gbgfx::drawTile2bpp` decodes.
- **1 bpp**: 8 bytes per 8x8 tile, one byte per row, pixel 0 in bit 7, bit set
  = ink (shade 3). This is what `gbgfx::drawTile1bpp` decodes, where a set bit
  paints black. The generator asserts that the `A` glyph ($80) is non blank,
  which is the polarity check the font has to pass: glyph pixels are shade 3,
  so the font renders dark on white.

## String tables

Several sections share one layout, called STRTAB below:

| Offset | Size | Field |
|---|---|---|
| 0 | 2 | `u16` entry count `c` |
| 2 | 2 `c` | `u16` offset of each string, measured from the start of the section |
| 2 + 2c | ... | the strings, each zero terminated ASCII |

Glyphs with no ASCII spelling are transliterated when the table is built, so
the firmware never sees them: `é` becomes `e` (POKeDEX), `♂` becomes `M` and
`♀` becomes `F` (NIDORAN M / NIDORAN F), `×` becomes `x`, `¥` becomes `$`.
`pokemon::gen1Encode` maps each of those back onto a real font tile.

## Section details

### `font`

Source: `gfx/font/font.png` (128x64, 1 bpp, 128 tiles) and
`gfx/font/font_extra.png` (128x16, 32 tiles; the PNG declares 2 bpp but only
uses two shades, so it converts losslessly to 1 bpp).

Exactly 2,048 bytes: 256 tiles of 8 bytes, **indexed by the Gen 1 character
code**, so tile index equals the byte the game stores in its tilemap. This is
what `gbgfx.cpp` expects and why the whole 256 tile page exists rather than the
ROM's two separate pages.

| Codes | Filled from | Notes |
|---|---|---|
| $00 to $5F | blank | control codes, no glyph |
| $60 to $7F | `font_extra.png` tiles 0 to 31 | text box border and punctuation; the ROM loads this at `vChars2` tile $60 |
| $80 to $FF | `font.png` tiles 0 to 127 | A = $80, Z = $99, a = $A0, `'` = $E0, `-` = $E3, `?` = $E6, `!` = $E7, `.` = $E8, `▷` = $EC, `▶` = $ED, `▼` = $EE, `♂` = $EF, `¥` = $F0, `×` = $F1, `/` = $F3, `,` = $F4, `♀` = $F5, 0 = $F6, 9 = $FF |

The generator refuses to write a pack whose $80 tile is blank, which catches an
inverted PNG polarity.

### `font_extra`

The same 32 tiles as codes $60 to $7F above, on their own, 1 bpp, 8 bytes each.
Tile index = `code - $60`. Present so a view can reach the border and
punctuation page without slicing the 256 tile font.

Layout doc names: `┌` $79 (index 25), `─` $7A (26), `┐` $7B (27), `│` $7C (28),
`└` $7D (29), `┘` $7E (30), space $7F (31).

### `font_battle`

Source: `gfx/font/font_battle_extra.png` (120x16, 30 tiles). The ROM loads it
at `vChars2` tile $62 (`home/load_font.asm`), so it overrides codes $62 to $7F
in battle and party contexts.

32 tiles of 16 bytes, **2 bpp**, tile index = `code - $60`. Indices 0 and 1
(codes $60, $61) are blank padding; indices 2 to 31 hold the sheet. This page
stays 2 bpp because the HP bar fill band is genuinely shade 2 in the ROM tile,
which the layout doc's HP bar colour rule depends on.

Codes the layout doc uses: $62 left cap, $63 empty fill, $64 to $6A partial
fill of 1 to 7 px, $6B full fill, $6C right cap (party menu), $6D right cap
(battle), $6E `<LV>`, $70 `to`, $71 `HP:`, $73 `<ID>`, $74 `№`.

### `border`

9 tiles, 1 bpp, in the order `gbgfx::drawBox` indexes them: top-left, top,
top-right, left, centre, right, bottom-left, bottom, bottom-right. Taken from
`font_extra.png` at codes $79, $7A, $7B, $7C, $7F, $7C, $7D, $7A, $7E. The game
uses one vertical rule tile ($7C) on both sides and one horizontal ($7A) on top
and bottom; the centre is the blank space tile $7F.

### `townmap_tiles`, `townmap_map`, `townmap_cursor`

- `townmap_tiles`: `gfx/town_map/town_map.png` (32x32), 16 tiles, 2 bpp,
  row-major. Tile index 0 to 15 is what `townmap_map` stores.
- `townmap_map`: `gfx/town_map/town_map.rle` (171 bytes) expanded with the
  ROM's nibble-pair RLE from `LoadTownMap`: for each source byte, the high
  nibble is the tile index and the low nibble is the run length, a `$00` byte
  ends the stream. The ROM adds $60 to the tile index because its tiles live at
  VRAM $60; this section stores the raw 0 to 15 index instead. Exactly 360
  bytes, row-major over a 20 wide by 18 tall grid, so cell `(cx, cy)` is at
  `cy * 20 + cx`.
- `townmap_cursor`: `gfx/town_map/town_map_cursor.png` (16x16). The source is
  1 bpp; it is widened to 2 bpp here (shades 0 and 3 only) so a view can blit
  it with the same 2 bpp path as everything else, with shade 0 transparent.
  4 tiles, row-major.

### `map_names` and `townmap_entries`

`map_names` is a STRTAB of the distinct location name strings from
`data/maps/names.asm`, in the order they are first referenced by
`data/maps/town_map_entries.asm` (outdoor table first, then indoor). 53 entries.

`townmap_entries` is 248 fixed records, one per map id, 3 bytes each:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | town map cell x, 0 to 19 |
| 1 | 1 | town map cell y, 0 to 17 |
| 2 | 1 | index into `map_names` |

**The indoor group logic is already resolved**, so the firmware never walks it.
The generator reproduces `LoadTownMapEntry`: a map id below `FIRST_INDOOR_MAP`
($25) reads `ExternalMapEntries[id]` directly; any higher id scans
`InternalMapEntries` for the first record whose `INDOORGROUP_*` threshold
exceeds the id, and that record's coordinate and name are written into the
record for that id. Every indoor map therefore already carries its outdoor
parent's cell, which is what the Home view's cursor needs.

### `map_labels`

STRTAB of 248 readable names, indexed by map id, derived from the map constant
in `constants/map_constants.asm`: `REDS_HOUSE_1F` becomes `Reds House 1F`.
Rule: split on `_`, capitalise each word, but leave a word untouched when it
contains a digit (`1F`, `B2F`, `2F`) or is one of `SS HQ PC TM HM`. Map ids
with no constant (there are none in this checkout) get an empty string. This is
the fallback label for maps that are not on the town map; the town map's own
prettier strings are in `map_names`.

### `badges`, `leader_faces`, `badge_numbers`

Source `gfx/trainer_card/badges.png` (16x256, 2 bpp). The sheet is 8 groups of
4 tile rows: for badge k, rows 4k and 4k+1 are the gym leader's face and rows
4k+2 and 4k+3 the badge, which is exactly the `+4` that `DrawBadges` applies.

- `badges`: 8 badges, each a 16x16 image as 4 tiles row-major (top-left,
  top-right, bottom-left, bottom-right), 64 bytes per badge, in gym order
  (Boulder, Cascade, Thunder, Rainbow, Soul, Marsh, Volcano, Earth).
- `leader_faces`: the 8 faces, same shape, same order. The Home view draws a
  face dimmed where the badge is not yet earned.
- `badge_numbers`: `gfx/trainer_card/badge_numbers.png` (16x32), 8 tiles,
  2 bpp, row-major. Tile k is the `[k+1]` marker.

### `icons` and `icon_map`

The ROM does not store party icons as finished 16x16 images. It loads two tiles
and builds the right half with the OAM x-flip bit
(`WriteSymmetricMonPartySpriteOAM`), except the helix icon, which is
asymmetric and uses four real tiles
(`WriteAsymmetricMonPartySpriteOAM`). **All of that is baked out here**: every
icon in the pack is a finished 16x16 image of 4 tiles, row-major, and the
firmware just blits it.

`icons` layout:

| Offset | Size | Field |
|---|---|---|
| 0 | 2 | `u16` icon count (15) |
| 2 | 2 | `u16` tiles per icon (4) |
| 4 | 64 each | the icons, in icon id order, 4 tiles of 16 bytes |

Icon id is the `ICON_*` constant from `constants/icon_constants.asm`:
$0 MON, $1 BALL, $2 HELIX, $3 FAIRY, $4 BIRD, $5 WATER, $6 BUG, $7 GRASS,
$8 SNAKE, $9 QUADRUPED, $A to $D unused (blank tiles in this pack), $E
TRADEBUBBLE. Source tiles, from `data/icon_pointers.asm`, first animation
frame only (the layout doc draws frame 0):

| Icon | Source PNG | Tiles used |
|---|---|---|
| MON | `gfx/sprites/monster.png` | 12 (top), 14 (bottom), mirrored |
| BALL | `gfx/sprites/poke_ball.png` | 0, 2, mirrored |
| HELIX | `gfx/sprites/fossil.png` | 0, 1, 2, 3, no mirroring |
| FAIRY | `gfx/sprites/fairy.png` | 12, 14, mirrored |
| BIRD | `gfx/sprites/bird.png` | 12, 14, mirrored |
| WATER | `gfx/sprites/seel.png` | 0, 2, mirrored |
| BUG | `gfx/icons/bug.png` | 2, 3, mirrored |
| GRASS | `gfx/icons/plant.png` | 2, 3, mirrored |
| SNAKE | `gfx/icons/snake.png` | 0, 1, mirrored |
| QUADRUPED | `gfx/icons/quadruped.png` | 0, 1, mirrored |
| TRADEBUBBLE | `gfx/trade/bubble.png` | 0, 2, mirrored |

`icon_map` is 151 bytes, `icon_map[dex - 1]` is the icon id for that species. It
is `data/pokemon/menu_icons.asm` with its packed nybbles unpacked; that table
is already in dex order, so no reordering is applied.

### `front`, `front_index`, `back`, `back_index`

Sources `gfx/pokemon/front/*.png` and `gfx/pokemon/back/*b.png`, 2 bpp,
row-major tiles, uncompressed (the `.pic` Gray-code plus RLE stage the ROM uses
is skipped; it buys nothing on a device with a filesystem).

`front_index` and `back_index` are 151 records of 5 bytes, **record `i`
describes dex number `i + 1`**:

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | `u32` offset into `front` / `back` |
| 4 | 1 | `sizeTiles`, the pic's side in tiles |

`sizeTiles` is 5, 6 or 7 for front pics (40x40, 48x48, 56x56) and always 4 for
back pics (32x32). Byte length of a pic is `sizeTiles * sizeTiles * 16`. The
two fossil pictures (`fossilaerodactyl`, `fossilkabutops`) are not species and
are not in the pack. The dex-number to file mapping comes from the `db DEX_*`
line in each `data/pokemon/base_stats/*.asm`, with the one filename fixup the
checkout needs (`mrmime` stats, `mr.mime` art).

### `player_walk`

`gfx/sprites/red.png` (16x96, six 16x16 frames). Three frames are packed, in
this order: **0 down, 1 up, 2 left**. Right facing is the left frame mirrored
horizontally, which is what the game does and what the layout doc asks for.
Each frame is 4 tiles row-major, 64 bytes, so the section is 192 bytes. Shade 0
is transparent.

### `tilesets`, `tileset_index`, `blocksets`, `blockset_index`

There are 24 tileset ids but only 19 distinct graphics sheets and 19 distinct
blocksets, because several ids share art (Reds House 1 and 2, Dojo and Gym,
Mart and Pokecenter, Forest Gate / Museum / Gate). The blobs hold one copy of
each distinct file; the index tables have 24 entries, and shared ids simply
point at the same offset. Sharing is resolved from the label chains in
`gfx/tilesets.asm`.

`tileset_index`, 24 records of 6 bytes, indexed by tileset id:

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | `u32` offset into `tilesets` |
| 4 | 2 | `u16` tile count (96 for most, 80 for cavern/club/plateau/reds_house, 32 for underground) |

`blockset_index`, 24 records of 6 bytes, indexed by the same tileset id, which
is how a tileset id resolves to its blockset:

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | `u32` offset into `blocksets` |
| 4 | 2 | `u16` block count |

A block is 16 bytes, 4x4 tile indices row-major into that tileset's graphics
(`BLOCK_WIDTH` = 4, confirmed by `DrawTileBlock`). `blocksets` is the raw
`gfx/blocksets/*.bst` bytes.

### `maps` and `map_index`

`maps` is the concatenation of the distinct `maps/*.blk` files, one byte per
block position, row-major, `width` bytes per row. **Maps that share a `.blk`
share one copy**: `maps.asm` stacks several `X_Blocks:` labels on one `INCBIN`
(all the little houses, the Pokecenters, the gate upper floors), and the
generator follows those label chains, so the 248 map ids resolve to 182 stored
blobs.

`map_index` is 248 records of 8 bytes, indexed by map id:

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | `u32` offset into `maps` |
| 4 | 1 | width in blocks |
| 5 | 1 | height in blocks |
| 6 | 1 | tileset id |
| 7 | 1 | border block index |

The map id to header association comes from `MapHeaderPointers`
(`data/maps/map_header_pointers.asm`), the one-entry-per-map-id table, not from
the `map_header` macro's own map constant. Two reasons: two header files claim
`UNDERGROUND_PATH_ROUTE_7` (the second is really the unused `_COPY` map and the
pointer table places it at the next id), and the unused map ids such as $0B and
$ED to $F4 deliberately alias a real header, which the pointer table gets right
and the constants do not. All 248 ids therefore have a usable record; a width
of 0 never occurs in this checkout but is still the "no such map" signal a
reader should check.

Width and height come from `map_const` for the header's own map constant, so
an aliasing id reports the size of the map it aliases (id $0B reports Saffron
City's 20x18), exactly as the ROM would render it. The tileset comes from the
map's `map_header` and the border block from the `db` at the top of
`data/maps/objects/<Map>.asm`.

### `dex_order`

190 bytes, `data/pokemon/dex_order.asm` verbatim. `dex_order[i]` is the dex
number of internal index `i + 1`, so an internal index `n` from WRAM reads
`dex_order[n - 1]`. A value of 0 is a MissingNo slot (39 of them).

### `species_names` and `base_stats`

`species_names` is a STRTAB of 151 entries **by dex number**, entry `i` being
dex `i + 1`. The ROM's `MonsterNames` is in internal index order, so the
generator reorders it through `dex_order`.

`base_stats` is 151 records of 9 bytes, record `i` for dex `i + 1`:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | base HP |
| 1 | 1 | base Attack |
| 2 | 1 | base Defense |
| 3 | 1 | base Speed |
| 4 | 1 | base Special |
| 5 | 1 | type 1 |
| 6 | 1 | type 2 (equal to type 1 for single types) |
| 7 | 1 | catch rate |
| 8 | 1 | front pic side in tiles, 5, 6 or 7 |

From `data/pokemon/base_stats/*.asm`. The sprite size is measured from the PNG
rather than read out of a compiled `.pic`, which gives the same number.

### `item_names` and `item_prices`

Both are **indexed directly by item id, 0 to 255**, not by a dense list,
because HM ids ($C4 to $C8) and TM ids ($C9 to $FA) are far away from the
ordinary items. Id 0 (`NO_ITEM`) is an empty name and a price of 0.

- `item_names`: STRTAB with 256 entries. Ids 1 to 83 and the floor names 84 to
  97 come from `data/items/names.asm`. HM and TM ids get the names the game
  prints procedurally, `HM01` to `HM05` and `TM01` to `TM50`. Ids with no item
  are empty strings.
- `item_prices`: 256 `u16` values. Ordinary items come from the BCD literals in
  `data/items/prices.asm`; TM prices come from `data/items/tm_prices.asm`,
  which stores thousands in a nybble array, multiplied by 1000; HMs and key
  items are 0, which the layout doc renders as `$    0`.

### `move_names` and `move_data`

`move_names` is a STRTAB of 165 entries, **entry `i` is move id `i + 1`**
(`POUND` is move id 1 and entry 0).

`move_data` is 165 records of 4 bytes, same 1-based keying:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | type |
| 1 | 1 | power |
| 2 | 1 | accuracy, out of 100 |
| 3 | 1 | base PP |

From `data/moves/moves.asm`. The ROM's accuracy byte is a 0 to 255 scaling of a
percentage; this section stores the percentage the source file writes, which is
what the layout doc's `ACC100` field prints. The animation and effect bytes are
dropped.

### `type_names` and `type_chart`

`type_names` is a STRTAB of 27 entries indexed by the type id from
`constants/type_constants.asm`: $00 NORMAL through $08 GHOST, the unused gap
$09 to $13, then $14 FIRE through $1A DRAGON. The unused gap repeats `NORMAL`,
exactly as `TypeNames` does.

`type_chart` is 82 records of 3 bytes, from `data/types/type_matchups.asm`:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | attacking type |
| 1 | 1 | defending type |
| 2 | 1 | multiplier times 10: 20, 15, 5 or 0 |

The record count is the section length divided by 3; the `-1` terminator is not
stored. Any pair absent from the table is neutral (10).

### `trainer_class`

STRTAB of 47 trainer class names from `data/trainers/names.asm`. **Entry `i` is
class id `i + 1`**, because `TrainerNames` starts at `YOUNGSTER` ($01) and
class $00 (`NOBODY`) has no name.

### `wild`

248 fixed-size records of 42 bytes, indexed by map id, so no pointer chasing:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | grass encounter rate, 0 means none |
| 1 | 20 | 10 grass slots, each {`u8` level, `u8` species internal index} |
| 21 | 1 | water encounter rate, 0 means none |
| 22 | 20 | 10 water slots, same shape |

Built from `data/wild/grass_water.asm` (one label per map id) and
`data/wild/maps/*.asm`. A rate of 0 zeroes its 10 slots, which matches the ROM,
where a zero-rate table is a single byte with no slots. Species are **internal
indices**, the same numbering the WRAM party structs use, so run them through
`dex_order` before touching `species_names` or `base_stats`. The layout doc's
fixed per-slot odds (51 51 39 25 25 25 13 13 3 3 out of 256, printed as 20 20
15 10 10 10 5 5 1 1 percent) are a firmware constant, not pack data.

Verified: map id $0C (`ROUTE_1`) has grass rate 25, ten slots holding only
Pidgey and Rattata at levels 2 to 5, and water rate 0. That matches
`data/wild/maps/Route1.asm` exactly.

### `items_placed`

104 records of 5 bytes, every item ball object event in the game, sorted by map
label:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | map id |
| 1 | 1 | x, in map steps |
| 2 | 1 | y, in map steps |
| 3 | 1 | item id |
| 4 | 1 | toggleable object index |

An item ball is an `object_event` with the 7 argument form, whose seventh
argument is the item id (`macros/scripts/maps.asm` tags it `ITEM | text_id`).
The x and y here are the source coordinates, not the `+4` the macro emits, so
they compare directly against `wXCoord` and `wYCoord`.

The **toggleable object index** is the game's pickup flag index, resolved here
so the firmware does not have to replicate the map-load logic. This checkout
calls the mechanism "toggleable objects" rather than the Gen 2 name "missable
objects". The index is the 0-based row number of the matching
`toggle_object_state` line in `ToggleableObjectStates`
(`data/maps/toggleable_objects.asm`), which is exactly
`(record offset) / 3` and is what the ROM's `ToggleableObjectFlagAction`
indexes with. The generator matches a ball to its row by the map-local object
constant: object constants in `data/maps/objects/*.asm` start at 1
(`object_const_def` is `const_def 1`) and run in `object_event` order, so the
n-th `object_event` is constant n. All 104 balls resolved; 255 would mark an
unresolved one.

Test the flag as `bit (index & 7)` of `wToggleableObjectFlags[index >> 3]`.

Note there are 119 `SPRITE_POKE_BALL` object events in the checkout but only
104 item balls: the rest are scenery or scripted balls (Oak's lab starters, for
instance) that use the plain 6 argument form and carry no item id.

### `items_hidden`

54 records of 5 bytes, one per row of `data/events/hidden_item_coords.asm`:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | map id |
| 1 | 1 | x |
| 2 | 1 | y |
| 3 | 1 | item id |
| 4 | 1 | hidden item flag index |

`HiddenItemCoords` carries only (map, x, y). The item id lives in the
per-map `data/events/hidden_events.asm` table, where an entry is a real ground
item only when its `dba` points at the `HiddenItems` routine; entries pointing
at `HiddenCoins` (the Game Corner floor coins) or at any other routine
(`OpenRedsPC`, bookcase and poster handlers) are not items and are excluded.
The generator joins the two tables on (map, x, y).

The **flag index** is the row's own 0-based position in `HiddenItemCoords`,
which is what `FindHiddenItemOrCoinsIndex` returns and what `FlagAction` uses
against `wObtainedHiddenItemsFlags` at $D6F0: byte `index >> 3`, bit
`index & 7`. All 54 rows matched an item event, so the flag index is dense,
0 to 53, and 54 is a plausible count against `MAX_HIDDEN_ITEMS` = 112.

Hidden coins are deliberately not in the pack; no view asks for them.

## Layout doc requests with no matching ROM asset

Checked against `docs/pokemon-aux-display-layout.md`:

- **Gym leader names.** The layout's badge row does not print them, and there
  is no leader name table in the ROM to pack: the names only exist as literal
  dialogue inside `text/PewterGym.asm` and friends. If a view ever wants
  `BROCK` under badge 1, it needs a hand written table in firmware, not a pack
  section.
- **`badge_numbers` as `[1]` to `[8]`.** The sheet really is 8 tiles and is
  packed, but the glyphs are bare digits in a frame; there is no separate
  bracket art.
- **Per-slot wild encounter odds.** Listed in the layout doc as pack-adjacent
  data; they are hard coded constants in `engine/battle/wild_mons.asm`, not a
  table, so they stay in firmware.
- Everything else the layout doc names (`battle_hud_1` to `_3`,
  `mon_nest_icon`, `gfx/battle/balls.png`) is marked "not used" there and is
  not packed.

## Deliberate deviations from the task brief

- `item_names` uses the shared STRTAB header (a `u16` count) rather than a
  `u8` count, because the table is indexed by item id and needs 256 entries,
  which does not fit in a byte.
- `font_battle` is the section name for the battle override page, because
  `font_battle_extra` is 17 characters and the container caps a name at 15.
- `font_battle` is 2 bpp, not 1 bpp: the HP bar fill tiles genuinely use three
  shades and the layout doc's bar colour rule depends on the shade 2 band.
- `townmap_cursor` is stored 2 bpp even though the source PNG is 1 bpp, as the
  brief asked, so every sprite in the pack takes the same blit path.

## growth

151 bytes, one per dex number (index = dex - 1): the species' growth rate as
the `GROWTH_*` index into the game's `GrowthRateTable` (`data/growth_rates.asm`,
rows Medium Fast, Slightly Fast, Slightly Slow, Medium Slow, Fast, Slow). The
firmware carries the six formulas and uses this to show experience to the
next level on the Battle view.

## sgb_palettes, sgb_pal_names, mon_palettes

The Super Game Boy colours the SGB-enhanced ROM uses, for a colour front end
(the e-paper never reads them).

- `sgb_palettes`: one 12 byte record per `PAL_*` constant in
  `constants/palette_constants.asm` order (`PAL_ROUTE` first, 37 in this
  checkout): four colours, RGB, 8 bits per channel scaled from the ROM's 5
  (`v * 255 / 31`). Colour 0 is the lightest (paper), colour 3 the darkest.
- `sgb_pal_names`: STRTAB of the constant names in the same order.
- `mon_palettes`: 152 bytes, index = dex number (0 = MissingNo), each the
  palette index of that species' picture, from `data/pokemon/palettes.asm`.
